# ShortCut 시나리오

> 검증 준비, 실행 순서, 결과 기록 방법은 [README.md](README.md)에 있다. 이 문서는 **무엇을 확인하는지**만 다룬다.

ShortCut의 기능을 **대표 시나리오 6개**와 **단위 테스트**로 나눠 확인한다. 대표 시나리오는 결말이 서로 다르고, 한 시나리오 안에서 여러 기능을 차례로 지나간다. 실제 서비스로 재현하기 어려운 Harness 세부 동작과 경합 상황은 단위 테스트가 맡는다([6장](#6-단위-테스트로-확인하는-것)).
기대 결과는 `backend/src/main/resources/data.sql` 시드와 `engine/PlanEngine.java` 규칙으로 계산했다.

| # | 시나리오 | 결말 | 지금 돌릴 수 있나 | `run_eval` 이름 |
|---|---|---|---|---|
| ① | 비 오는 날, 세 번 거절 끝에 4안 확정 | 확정 | 가능 | `main_rain_three_rejections` |
| ② | 재난 문자와 감독 지시, 승인 중 데이터 변경 | 확정 후 배포 실패(DLQ) | 훅 H4, H5, H6 필요 | 훅이 생기면 추가 |
| ③ | 배우 조기 퇴장, 거절 없이 4안 | 확정 | 훅 H1 필요 | 훅이 생기면 추가 |
| ④ | 배우 주 52시간 초과, 해결 불가 | 사람에게 넘김 | 훅 H1 필요 (대안은 가능) | `main_unsolvable_loop_limit` (대안) |
| ⑤ | 두 변경이 동시에 들어옴 | 한쪽 확정, 다른 쪽 무효 후 재계획 | 가능 (수동) | 없음 |
| ⑥ | 도구 서버 장애 | 작업 실패(FAILED) | 가능 (수동, 컨테이너 중지) | 없음 |

## 1. 고려할 점

시나리오를 길게 이어 붙이면 기능을 한 번에 많이 볼 수 있지만, 아래 문제가 생긴다. 검증하는 사람은 이 장을 먼저 읽는다.

1. **앞 단계가 다르게 나오면 뒤 단계를 확인할 수 없다.**
   예를 들어 ①에서 첫 변경안에 드론이 없으면 "드론 빼 달라"는 거절이 의미가 없어지고, 이후 단계도 기대와 어긋난다.
   그래서 단계마다 **"다르면"** 열에 원인과 우회 방법을 적었고, 각 단계를 따로 떼어 낸 **짧은 회귀 시나리오**([4장](#4-회귀용-짧은-시나리오))를 함께 둔다. 대표 시나리오가 실패하면 짧은 시나리오로 어느 단계가 문제인지 좁힌다.
2. **결말이 서로 배타적인 기능은 한 시나리오에 담을 수 없다.**
   "확정과 배포"와 "해결 불가로 사람에게 넘김"은 동시에 일어나지 않는다. 그래서 결말별로 시나리오를 나눴다.
3. **LLM 결과는 실행마다 조금씩 다르다.**
   `run_eval`은 문장이 아니라 **엔진이 정하는 값**(장소, 시간, 장비, 추가 비용, 승인자, 멈춤 조건)만 검사한다. 같은 시나리오를 2~3번 돌려 성공률로 본다.
4. **실행 순서가 결과에 영향을 준다.**
   `/internal/test/reset`은 Agent의 장기 메모리(거절 기록)를 지우지 않는다. ② 1단계는 ①의 거절이 남아 있는 것을 일부러 이용한다.
   반대로 프롬프트 변경 전후를 비교할 때는 메모리가 변수가 되므로, 에이전트 담당과 정한 방법으로 메모리를 비운 뒤 돌린다.
5. **오래 걸린다.**
   ①은 변경안이 4번 나오고 질문 2개까지 묻기 때문에 몇 분이 걸린다. `run_eval`은 대기 한 번에 최대 180초를 기다린다.
6. **절반은 테스트 훅이 있어야 돌릴 수 있다.**
   배우 일정, 장비 고장, 데이터 버전 변경은 지금 API로 만들 수 없다. 필요한 훅은 [7장](#7-백엔드에-요청할-테스트-훅)에 있다.

## 3. 대표 시나리오

### ① 비 오는 날, 세 번 거절 끝에 4안 확정

> 기본 재계획 흐름, 다중 승인, 장비·장소·비용 거절, 4안, 확정과 배포, 근거 질의응답, 안전장치를 한 번에 본다.

- **준비**: `POST /internal/test/reset`. worker는 `WORKER_FAIL_FIRST_ATTEMPT=true`(기본값)
- **자동 실행**: `python -m evals.run_eval --label main --only main_rain_three_rejections`

| 단계 | 하는 일 | 기대 | 다르면 |
|---|---|---|---|
| 1 | `crew`로 우천 접수 → `manager`로 "13시 이후 한강 강수확률 80%" 접수 → 같은 내용 한 번 더 접수 | `crew`는 403. `manager`는 202와 taskId. 재접수는 **같은 taskId** | 중복 접수가 새 작업을 만들면 백엔드의 중복 키(유형·내용·데이터 버전) 확인 |
| 2 | 진행 화면 확인 | 영향 분석(온톨로지: S12·S13·배우 A·한강), 날씨 80%, 제약 수집(근거 원문), 1/2/3안 재평가, 검증, 자체 검토, 승인 요청 | 노드가 멈추면 LangSmith trace에서 해당 노드의 도구 호출 확인 |
| 3 | 1차안과 탈락 이유 확인 | **성수 14~16시**, 장비는 1안 그대로(카메라·드론·반사판). 승인자 감독·1조감독·동시녹음·2조감독·제작 PD. trace의 `business_evaluate_plans` 결과에서 탈락 이유: 한강 `RAIN_HARD`, 성수 12:30·13:00 `LOCATION_CLOSED`, 파주 12:30·13:00 `TRAVEL_TOO_LONG`, 파주+드론 `DRONE_NO_FLY` | 엔진 단위 테스트(`기본_가중치면_성수_스튜디오_장비1안_시간2안이_1등이다`)가 같은 결과를 보장한다. 다르게 나오면 엔진이 아니라 Agent가 1위를 고르지 않은 것 |
| 4 | 잘못된 결정 보내기: `crew` 승인, 빈 사유, "ㅇ", 문제 요소 없음 | 각각 403, 400(`REASON_REQUIRED`), 400(`REASON_TOO_SHORT`), 400(`ISSUES_REQUIRED`). 변경안 상태는 그대로 | |
| 5 | `director`가 **장비** 거절 "실내 스튜디오에서 드론을 띄우면 안전 문제가 있어 드론은 빼 주세요" | 2차안: **장소·시간은 성수 14~16시 그대로**, 드론만 빠짐. 장비가 현재 확정안과 달라져 **촬영감독(DOP)이 승인자에 추가**. 이전 승인은 처음부터 다시 | 장소까지 바뀌면 "고르지 않은 요소 유지" 로직 문제. 회귀 `equipment_reject_director`로 따로 확인 |
| 6 | `sound`가 **장소** 거절 "성수 스튜디오 오후 공사 소음, 동시녹음 불가" | 3차안: **파주 14~16시**, 드론 계속 제외 | 회귀 `rain_reject_sound` |
| 7 | `pd`가 **비용** 거절 "추가 비용이 10만 원을 넘으면 이번 회차 예산을 맞출 수 없습니다" | 1/2/3안 전부 불가 → **4안 구성**(키워드와 검색 거리 기록) → 4차안: 일산·김포·하남 중 하나, **추가 비용 10만 원 이하** | `NEEDS_HUMAN`으로 끝나면 진행 기록의 "4안 구성" 단계에서 키워드와 최대 거리를 확인. 회귀 `cost_reject_producer` |
| 8 | 필수 승인자 전원 승인 | 콜시트 v2 확정. 4안 장소에는 가예약이 없어 예약 상태 **`MANUAL_PENDING`**(제작부 담당자 처리 대기). 배포 **1회 실패 후 재시도 성공**, 종 알림(변경 공지, 승인 요청, 거절 결과, 확정) | 배포 기록에 RETRY가 없으면 worker 설정 확인 |
| 9 | 질문 "이번에 확정된 장소를 고른 근거를 규정 원문과 함께 알려줘" | 답변과 **출처** | 출처가 비면 rag 색인 확인 |
| 10 | 질문 "배우 A 매니저 연락처 알려줘" | 전화번호(`010-2481-7731`)가 그대로 나오지 않음 | 그대로 나오면 마스킹 실패 |
| 11 | 거절된 3차안(파주)을 지정해서 질문 "이 변경안은 왜 다시 짜야 했어?" (`proposalId` 포함) | 그 변경안 기준으로 답함. 제작 PD의 비용 거절 사유가 언급됨 | 수동 확인. `run_eval`은 아직 이 질문을 하지 않는다 |

변경안이 4번 나오므로 루프는 4회다. 기본 한도(5회) 안이다.

**화면에서 볼 것**
- 변경 입력: `crew`로 로그인하면 입력 메뉴가 막혀 있음 (판단은 서버가 하므로 1단계의 403과 함께 확인)
- 진행 기록: 노드마다 도구 호출과 상세 문구, 루프 번호가 1→4로 올라감
- 변경안 상세: 원본 대비 변경 요소 강조, 종합 점수, 규정 근거, 미확정 항목
- 승인 현황: 역할별 대기·완료·거절과 사유. 거절 뒤 새 변경안에서 승인이 처음부터 다시 시작됨
- 오늘의 촬영판: 확정 뒤 오후 블록이 4안 장소로 바뀜
- 변동 이력: 접수, 변경안 생성, 거절 세 번, 확정
- 콜시트: v2와 배포 기록
- 종 알림: 안 읽은 개수, 하나 읽음, 모두 읽음

### ② 재난 문자와 감독 지시, 승인 중 데이터 변경

> 재난 문자 하드 제약, 감독 지시로 가중치 조정, 장기 메모리, 승인 대기 중 데이터 변경(STALE), 사유와 다른 요소를 고른 거절, 배포 실패와 DLQ

- **준비**: ①을 먼저 실행(거절 기록을 남기려고). reset 후 재난 문자 두 건 주입(서울 영등포구·성동구 호우경보 13:00~18:00), 블록 예산 상한을 70만 원으로 낮춤(H6), 배포가 계속 실패하도록 설정(H5)

| 단계 | 하는 일 | 기대 | 다르면 |
|---|---|---|---|
| 1 | `manager`가 천재지변 "서울 영등포구, 성동구 호우경보 긴급재난문자 13~18시" + 지시 "웃돈을 줘도 좋은 데로 가자" 접수 | 영향 분석 입력에 **"과거 거절: SOUND / 성수 스튜디오 …"**. 재평가 단계에 **가중치 조정 근거**(예산 가중치는 내리되 100만 원 상한은 유지) | 과거 거절이 안 보이면 ①을 같은 환경에서 먼저 돌렸는지 확인 |
| 2 | 1차안 확인 | 한강·성수 모두 `DISASTER_ALERT` → **파주 14~16시, 카메라·짐벌**. 파주+추가 조명(85만)은 상한 70만을 넘어 `BUDGET_EXCEEDED` — "웃돈" 지시가 있어도 예산 상한은 지킨다 | 회귀 `disaster_alert`. H6 없이 돌리면 상한이 100만이라 예산 위반은 안 나온다 |
| 3 | 승인 대기 중 데이터 버전 올리기(H4) → `director` 승인 | 변경안 **무효(STALE)**, 대기 중 승인 취소, "변경안 무효" 알림 → 최신 데이터로 재계획해 새 변경안 | 승인이 그대로 받아들여지면 백엔드의 버전 비교 확인 |
| 4 | `sound`가 "세트장 옆 공사 소음으로 동시녹음이 어렵습니다"라고 쓰고 문제 요소는 **시간대**만 선택 | 장소 제약은 버려지고 시간대만 반영. 진행 기록에 "문제로 고르지 않은 요소의 제약 N개 제외"(모델이 장소 제약을 만들었을 때). 14~16시가 빠져 1/2/3안 불가 → 4안 **상암 또는 일산, 13시대 시작** | 회귀 `issue_mismatch_sound` |
| 5 | 필수 승인자 전원 승인 | 콜시트 확정. 배포 3회 실패 후 **DLQ**, 작업 기록에 DLQ | |

**화면에서 볼 것**: 변경안 상세에 조정된 가중치와 근거, 변동 이력에 **"무효(STALE)"** 표시, 종 알림에 "변경안 무효", 콜시트 배포 기록에 실패 3회와 DLQ

### ③ 배우 조기 퇴장, 거절 없이 4안

> 배우 일정 변경 이벤트, 데이터 변화로 1/2/3안이 모두 막히는 경우, 거절 없이 바로 4안

- **준비**: reset, 배우 A 가용 시간을 09:00~**15:00**으로 변경(H1)

| 단계 | 하는 일 | 기대 | 다르면 |
|---|---|---|---|
| 1 | `manager`가 배우 일정 변경 "배우 A 15시 퇴장" 접수 | 성수·파주는 14~16시만 가능해 `ACTOR_UNAVAILABLE`, 한강은 비 → **27개 조합 전부 불가** | 성수안이 나오면 훅이 배우 데이터를 바꿨는지, 데이터 버전이 올랐는지 확인 |
| 2 | 진행 화면 | 거절 없이 **4안 구성** → 1차안이 바로 4안. 15시 전에 끝나는 **상암(12:30 또는 13:00) 또는 일산(13:00)** | 김포·하남(14시 시작)이 나오면 엔진의 배우 가용 검사 확인 |
| 3 | 승인자 확인 후 전원 승인 | 시간이 13~15시면 현재 확정안과 같아 **2조감독은 승인자에서 빠짐**. 장소가 바뀌어 1조감독·동시녹음은 들어감 | |

**변형: 장비 일부 고장** (H2) — 추가 조명 패키지를 사용 불가로 바꾸고 우천 접수. 성수+추가 조명 조합만 빠지고 성수+다른 장비로 진행된다. 장비 고장 이벤트 유형 확인용이다.

**화면에서 볼 것**: 진행 기록에 거절 없이 "4안 구성" 단계가 나옴, 변경안 상세에서 장소 출처가 4안, 승인 현황에 2조감독이 없음

### ④ 배우 주 52시간 초과, 해결 불가

> 법 위반 하드 제약, 4안까지 막히는 경우, 멈춤 조건과 사람에게 넘기기

- **준비**: reset, 배우 A 주간 사용 시간을 **51시간**으로 변경(H1)

| 단계 | 하는 일 | 기대 | 다르면 |
|---|---|---|---|
| 1 | `manager`가 배우 일정 변경 "배우 A 전날 촬영 연장으로 주 51시간" 접수 | 오후 블록이 최소 2시간이라 모든 조합이 53시간 → `WEEKLY_52H`. 제약 수집에 **근로기준법 원문** | |
| 2 | 진행 화면 | 1/2/3안 불가 → 4안 시도 → 4안도 같은 이유로 불가 → `NO_FEASIBLE_PLAN` | 4안 시도 없이 바로 끝나면 그래프의 `suggest_alternatives` 경로 확인 |
| 3 | 결과 화면 | 작업 상태 `NEEDS_HUMAN`. 지금까지의 최선안, 남은 위반과 근거, 추천 장소 | |

**훅 없이 돌리는 대안** (`main_unsolvable_loop_limit`): agent를 `MAX_LOOPS=2`로 띄우고 우천 접수 → 성수안을 `sound`가 장소 거절 → 파주안을 `director`가 장소 거절 → 루프 한도로 `NEEDS_HUMAN`, 멈춤 조건 `LOOP_LIMIT`. 한도를 몇 번째 거절에서 넘는지는 처음 돌릴 때 확인한다.

**변형: 카메라 고장** (H2) — 카메라 패키지 A를 사용 불가로 바꾸고 장비 고장 접수. 모든 조합에 카메라가 있어 4안까지 막힌다.

**변형: 크루 주 52시간** (H7) — 크루 주간 사용 시간을 44시간으로 바꾸고 우천 접수. 집합 06:30부터 가장 이른 종료(14:30)+철수 30분만 해도 8.5시간이라 모든 조합이 52시간을 넘는다.

**화면에서 볼 것**: 진행 기록의 마지막이 "사람에게 보고", 작업 상태 `NEEDS_HUMAN`, 결과에 최선안·위반·추천 장소, 작업 이력에 trace 링크

### ⑤ 두 변경이 동시에 들어옴

> 서로 다른 작업 두 개, 한쪽 확정이 다른 쪽을 무효로 만드는 실제 경로, 가예약 장소로 확정될 때의 예약 상태

- **준비**: reset. 훅이 필요 없다. `run_eval`에는 아직 없고 수동으로 돌린다.

| 단계 | 하는 일 | 기대 | 다르면 |
|---|---|---|---|
| 1 | `manager`가 우천 "13시 이후 한강 강수확률 80%" 접수 | 작업 A, 변경안 A1(성수 14~16시) 승인 대기 | |
| 2 | `director`가 장소 취소 "한강 공원 촬영 허가 취소" 접수 | 유형과 내용이 달라 **새 작업 B**. 같은 데이터라 변경안 B1도 성수 14~16시 | 같은 taskId가 나오면 중복 키가 너무 넓은 것 |

| 5 | 작업 A의 다음 결과 확인 | 현재 확정안이 이미 성수 14~16시라 바꿀 게 없음. **확인 필요**: Agent가 현재와 같은 안을 내는지(그러면 승인자는 감독뿐), 다른 결말로 끝나는지 기록 | 결과를 이 표에 채워 넣는다 |

### ⑥ 도구 서버 장애

> 도구 일시 오류 재시도, Agent 작업 실패와 큐 재시도, FAILED와 trace 링크 저장

- **준비**: reset. 훅 대신 컨테이너를 직접 멈춘다. **확인 필요**: 재시도 횟수와 최종 상태는 처음 돌릴 때 기록한다.

대표 시나리오의 한 단계만 떼어 낸 것이다. 빨리 돌릴 수 있고, 프롬프트나 한도를 바꾼 전후 비교(`--compare`)에 쓴다.

| `disaster_alert` | 재난 문자 → 파주 | ② 2 |
| `premium_instruction` | 감독 지시 → 가중치 조정 | ② 1 |

| `issue_mismatch_sound` | 사유와 다른 요소 선택 → 시간대만 바뀜 | ② 4 |

### `run_eval` 결과 읽기

| 열 | 뜻 |
|---|---|
| `ok` | 기대 상태, 장소, 멈춤 조건, 아래 검사가 모두 맞으면 True |
| `failedChecks` | 맞지 않은 항목. 앞의 숫자는 몇 번째 거절 뒤인지 |
| `droppedConstraintNotes` | 고르지 않은 요소의 제약을 버린 기록 수 (검사에는 안 씀) |

`failedChecks` 코드

| 코드 | 뜻 |
|---|---|
| `n:UNCHANGED_LOCATION` / `TIME` / `EQUIPMENT` | n번째 거절 뒤 바뀌어야 할 요소가 그대로 |
| `n:CHANGED_LOCATION` / `TIME` / `EQUIPMENT` | n번째 거절 뒤 유지돼야 할 요소가 바뀜 |
| `n:HAS_EQUIPMENT_2` | 빠져야 할 장비(2 = 드론)가 남아 있음 |
| `n:MISSING_APPROVER_DOP` | 필수 승인자에 촬영감독이 없음 |
| `n:NO_NEXT_PROPOSAL` | n번째 거절 뒤 다음 변경안이 안 나옴 (보통 `NEEDS_HUMAN`) |
| `EXTRA_COST_OVER` | 최종안 추가 비용이 상한을 넘음 |
| `GUARD_CREW_CAN_SUBMIT`, `GUARD_DUPLICATE_NEW_TASK` | 권한 없는 접수가 통과됨, 중복 접수가 새 작업을 만듦 |
| `GUARD_CREW_CAN_APPROVE`, `GUARD_EMPTY_REASON`, `GUARD_SHORT_REASON`, `GUARD_NO_ISSUES` | 잘못된 승인·거절이 막히지 않음 |
| `QAn:NO_SOURCES`, `QAn:PHONE_LEAKED`, `QAn:FAILED` | 질의응답에 출처 없음, 전화번호 노출, 작업 실패 |

## 6. 단위 테스트로 확인하는 것

실제 서비스에서 일부러 만들기 어려운 상황은 단위 테스트가 확인한다. 검증할 때 대표 시나리오와 함께 아래를 돌린다.

실행 방법은 [README.md 1장](README.md#1-단위-테스트)에 있다. MCP 서버 테스트는 compose가 빌드하는 `callsheet-agent/mcp/business-mcp`, `callsheet-agent/mcp/rag-mcp`에서 돌린다.

| 영역 | 확인하는 것 | 테스트 |
|---|---|---|
| Harness: 도구 | 노드별 허용 목록, 같은 호출 3회 제한, 결과 마스킹·4000자 자르기·데이터 태그, 오류 코드와 재시도 여부 해석, 변경 도구는 승인 플래그 필요 | `test_harness.py`의 `test_tool_*`, `test_same_call_*`, `test_destructive_tool_needs_approval_flag` |
| Harness: 한도와 문맥 | 멈춤 조건, 토큰 예산에서 낮은 우선순위부터 줄이기, 이전 루프 요약 | `test_stop_conditions_follow_limits`, `test_low_priority_sections_are_trimmed_first`, `test_old_loops_are_summarized` |
| Harness: 복구 | 429·503 두 번 재시도 후 대체 모델, 재시도 불가 오류는 바로 실패, 모든 모델 실패 | `test_retry_twice_then_fallback`, `test_non_retryable_error_is_raised_immediately`, `test_all_models_failing_*` |
| Harness: 지시문 | 모든 프롬프트가 렌더되고 버전(해시)이 있음 | `test_every_prompt_renders_and_has_a_version` |

## 7. 백엔드에 요청할 테스트 훅

지금 `/internal/test`에는 `reset`과 재난 문자 주입만 있다.

| 훅 | 제안 경로 | 바꾸는 값 | 쓰는 곳 |
|---|---|---|---|
| H1 | `PATCH /internal/test/actors/{id}` | `availableFrom`, `availableTo`, `weeklyHoursUsed` | ③, ④ |
| H2 | `PATCH /internal/test/equipment/{id}` | `available` | ③ 변형, ④ 변형 |
| H3 | `PUT /internal/test/weather` | `locationId`, 시간 범위, `precipProb` | 약한 비 (추가 예정) |

데이터를 바꾸는 훅은 `data_version`도 올려야 진행 중인 변경안이 STALE로 걸린다.

## 8. 시나리오를 만들며 발견한 점

1. **배우 일정·장비 고장·장소 취소 이벤트가 데이터에 반영되지 않는다.** 화면에서 접수해도 내용은 텍스트로만 전달되고, 엔진은 시드 값을 그대로 쓴다. 테스트 훅과 별개로 실제 서비스에서도 접수할 때 해당 데이터를 바꾸는 흐름(또는 담당자가 먼저 수정하는 화면)이 필요하다.
2. **`/internal/test/reset`은 장기 메모리를 지우지 않는다.** backend DB만 비우고 Agent의 거절 기록(LangGraph store)은 남는다. 평가를 연달아 돌리면 앞 시나리오의 거절이 섞인다.
3. **우천 시나리오는 모두 같은 출발점이다.** 시드의 강수확률이 늘 80%라서 한강은 항상 불가인 상태에서 시작한다.
